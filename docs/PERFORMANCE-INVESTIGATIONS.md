# Areas to investigate behind the C# scanner lag

**Deferred backlog only.** The user explicitly asked to leave both optimization
and deeper investigation for later. The checks below are ideas, not active tasks
or authorization to run them.

The [existing comparison](./PERFORMANCE.md) measured the current C# Native AOT port at 1.87–2.67× Go’s elapsed time for `Reset + SetText + Scan`. C# allocated 6.352, 12.464 and 21.493 bytes per input byte on real, ASCII and Unicode workloads, versus Go’s 1.505, 0.045 and 0.930. These are measured totals, not attribution to individual methods. No new benchmark, profile, optimization or executable-source change was made for this note.

The priorities below follow concrete implementation differences; their contribution to elapsed time remains unmeasured.

1. **Input conversion and its GC effects.** [SetText(byte[])](../src/TypeScript.Scanner/Scanner/Scanner.cs#L3703) calls [Latin1 decoding](../src/TypeScript.Scanner/Runtime/GoString.cs#L18), allocating a UTF16 string with one character per input byte on every timed file pass. [Go SetText](../upstream/TypeScript/tsc/internal/scanner/scanner.go#L397) binds its preloaded string. The C# backing payload alone is approximately two allocated bytes per input byte, before headers; it cannot explain all the measured allocation totals. The 256KiB synthetic inputs also produce large source-string objects. Existing samples show C# Gen2 collections on those workloads and none on the smaller real files, but no GC-pause attribution was collected. **Smallest check:** measure `Reset + SetText` alone on the existing inputs, recording allocation volume and GC pause time; do not assume its isolated time subtracts cleanly from the combined scan.

2. **Copied internal token values instead of substring views.** The [ASCII identifier fast path](../src/TypeScript.Scanner/Scanner/Scanner.cs#L2042) materializes `Substring`; [upstream](../upstream/TypeScript/tsc/internal/scanner/scanner.go#L1498) stores a source-string slice. [Plain strings](../src/TypeScript.Scanner/Scanner/Scanner.cs#L2186) and [number fragments](../src/TypeScript.Scanner/Scanner/Scanner.cs#L2894) also copy text. These paths run even though benchmark code never requests public token-value getters. They may account for substantial per-token allocation and copying. **Smallest check:** collect one allocation-stack sample on the unchanged ASCII workload and quantify internal substring/string allocations against the recorded total.

3. **Builder and escape-helper intermediates.** [Number-fragment scanning](../src/TypeScript.Scanner/Scanner/Scanner.cs#L2841) eagerly creates [GoBuilder/StringBuilder](../src/TypeScript.Scanner/Runtime/GoString.cs#L105), even when there are no separators; [Go’s zero-value builder](../upstream/TypeScript/tsc/internal/scanner/scanner.go#L2048) can return a slice without a backing buffer. Escaped strings additionally use builders, [per-rune string encoding](../src/TypeScript.Scanner/Runtime/GoString.cs#L9) and [surrogate sentinels](../src/TypeScript.Scanner/StringUtil/Util.cs#L20). Allocation/encoding overhead is plausible, particularly in the string stress input. **Smallest check:** attribute builder, buffer and small-string allocations in one existing Unicode-workload trace, separating ordinary numbers from escaped strings.

4. **Numeric conversion and cache misses.** [FromString](../src/TypeScript.Scanner/JsNum/String.cs#L87) builds a rune list/array; [integer parsing](../src/TypeScript.Scanner/JsNum/String.cs#L144) uses BigInteger arithmetic for every accepted integer, while [Go first tries ParseInt](../upstream/TypeScript/tsc/internal/jsnum/string.go#L149). Fractional formatting also constructs intermediate strings. [Numeric caching](../src/TypeScript.Scanner/Scanner/Scanner.cs#L3074) helps within each file, but benchmark resets clear entries between passes. **Smallest check:** count conversion calls/cache hits and sample their CPU/allocations on the existing numeric workload; separate small integers, rounding boundaries and fractions before proposing changes.

5. **Per-token work and generated code.** ASCII has 52,033 tokens per 262,224 bytes, compared with 12,573 per 176,279 real-source bytes. Token materialization, dictionary hashing, dispatch and the [benchmark checksum](../benchmarks/Scanner.Benchmarks/Program.cs#L24) could therefore amplify per-token costs. The [predicate-based ASCII loop](../src/TypeScript.Scanner/Scanner/Scanner.cs#L350), Native AOT inlining/bounds checks and runtime collections are lower-confidence possibilities; source shape alone proves no code-generation disadvantage. **Smallest check:** vary token density at fixed input bytes in a future diagnostic workload; separately quantify checksum overhead with output validation outside timing. Inspect native code only for hot methods established by a CPU sample.

Public `TokenText`/`TokenValue` getters, directive snapshots/Mark/Rewind and parser-directed regex/JSX/template rescans were not exercised and cannot explain this measured gap. Allocation ratios do not establish timing shares; one host and five short samples do not support intrinsic language claims or speed guarantees.

Any later change must retain the pinned upstream algorithms, byte offsets, invalid UTF8/lone-surrogate semantics and numeric rounding, and pass the [correctness and Native AOT gates](./VERIFICATION.md).
