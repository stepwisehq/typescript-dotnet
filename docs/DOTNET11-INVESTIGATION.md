# .NET 11 text APIs: deferred investigation notes

**Deferred at the user’s request.** These preliminary notes were gathered before the
pause; they are not an adoption review or an accepted optimization plan. Resume only
after initial implementation is complete and the user authorizes this work. No further

Investigated **2026-10-09**, against delivery commit `37bd57d`. This is a documentation-only investigation, not an adoption decision. The accepted port remains on the SDK pinned by [global.json](../global.json), **10.0.401**, with its existing [Linux x64 proof](../validation/results/configuration-verified.json). ## Release and API status

The supplied [Microsoft Learn overview](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/libraries#text-serialization-and-data-handling) describes real additions. Microsoft's [11.0 release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/11.0/releases.json), read on the investigation date, identifies the latest release as **11.0.0-rc.1**, released **2026-09-08**, SDK **11.0.100-rc.1.26425.128**, with support phase `go-live`. The [official RC1 notes](https://github.com/dotnet/core/blob/main/release-notes/11.0/preview/rc1/11.0.0-rc.1.md) agree. Go-live status does not make this a final release or establish compatibility with this port.

The overview is a rolling document, updated after RC1. This investigation checked important candidates against the **RC1 runtime tag**, rather than assuming every current announcement shipped in RC1. UTF validation/search, String Rune overloads and TextInfo Rune casing are present there. The API documentation carries a prerelease warning. Conversely, the overview's newer numeric-converter announcements, such as `BFloat16Converter`, are absent from the checked [RC1 System.Text.Json reference](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Text.Json/ref/System.Text.Json.cs); they should not be treated as verified RC1 capabilities.

## Concrete opportunities and limits

| Addition | Applicability to this port |
| --- | --- |
| `Utf8.IndexOfInvalidSubsequence`, `Utf16.IsValid` and `Utf16.IndexOfInvalidSubsequence` | Best bounded candidate: explicit validation at the Unicode/OS boundary in [PathByteText](../src/TypeScript.Scanner/TsPath/PathByteText.cs) and [LinuxReadPaths](../src/TypeScript.Scanner/Vfs/OsVfs/LinuxReadPaths.cs). They expose a failure index without exception-driven validation. They still require actual byte spans or actual Unicode text. Applying UTF16 validation to the Latin1-shaped internal byte string would validate the wrong representation. `Utf8.IsValid` itself already exists in .NET 10; only the indexed UTF8 search is new here. |
| String search/replace/split/trim with `Rune` | Convenient for genuine Unicode-facing display or host strings. RC1 [String.Searching](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Private.CoreLib/src/System/String.Searching.cs) encodes a Rune into one or two UTF16 characters and searches that span. Returned indices remain UTF16 positions, not UTF8 byte offsets. This does not replace [Scanner](../src/TypeScript.Scanner/Scanner/Scanner.cs) token positions or its byte-to-UTF16 mapping. Most path delimiters are ASCII already, so no large simplification is apparent. |
| `TextInfo.ToLower/ToUpper(Rune)` and character comparison options | No direct replacement for [UnicodeCase](../src/TypeScript.Scanner/Runtime/UnicodeCase.cs), its pinned Go tables, simple-fold or special filename canonicalization. [TextInfo's implementation](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Private.CoreLib/src/System/Globalization/TextInfo.cs) uses globalization casing; culture/provider/version behavior is not the original pinned algorithm. |
| Base64 span/convenience additions | Possible allocation or convenience improvement for ordinary byte-preserving API/validation envelopes. They do not improve scanner semantics, make malformed text representable, or justify changing canonical evidence. Existing Convert APIs already suffice. No measured bottleneck establishes priority. |
| JSON metadata, source-generation, writer reuse and JSONL additions | Could simplify authored transport code such as [Configuration.Validation](../validation/Configuration.Validation/Program.cs). RC1 includes typed `GetTypeInfo<T>`/`TryGetTypeInfo<T>`, writer reset with options and `SerializeAsyncEnumerable` with a `JsonTypeInfo<T>` overload suitable for the existing static-metadata approach. The options-only overload has trimming/dynamic-code warnings. This is separate from the mapped [JsonCodec](../src/TypeScript.Scanner/Json/JsonCodec.cs). |
| Regex engine fixes and `AnyNewLine` | Runtime fixes might benefit the existing nonbacktracking engine, but performance is unmeasured. `AnyNewLine` changes grammar and must not be enabled in [Semver](../src/TypeScript.Scanner/Semver/Version.cs): the port deliberately preserves Go ASCII classes, case folding and strict end anchors. |

The UTF APIs' exact contracts are in [Utf8.IndexOfInvalidSubsequence](https://learn.microsoft.com/en-us/dotnet/api/system.text.unicode.utf8.indexofinvalidsubsequence?view=net-11.0) and [Utf16.IsValid](https://learn.microsoft.com/en-us/dotnet/api/system.text.unicode.utf16.isvalid?view=net-11.0), with RC1 implementations in [Utf8](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Private.CoreLib/src/System/Text/Unicode/Utf8.cs) and [Utf16](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Private.CoreLib/src/System/Text/Unicode/Utf16.cs). They return `-1` for valid input and otherwise identify the first invalid subsequence. Validation does not transcode, preserve invalid bytes through a Unicode string, or supply Go error text.

## Semantic gaps these APIs do not close

[GoString](../src/TypeScript.Scanner/Runtime/GoString.cs) deliberately stores one char per byte. Arbitrary invalid UTF8 remains observable, and Go decoding consumes **one byte** for an invalid sequence. .NET's [Rune.DecodeFromUtf8](https://github.com/dotnet/runtime/blob/v11.0.0-rc.1.26425.128/src/libraries/System.Private.CoreLib/src/System/Text/Rune.cs) deliberately consumes a Unicode maximal invalid subpart, which can span multiple bytes. Replacing the decoder would change iteration, offsets and diagnostics. Rune was already available before .NET 11; the new String overloads do not change this distinction.

JavaScript string literals also preserve escaped lone surrogates through [EncodeJSStringRune](../src/TypeScript.Scanner/StringUtil/Util.cs). Strict scalar validation belongs at an explicit filesystem boundary, not in scanner strings, configuration values or virtual path keys. Actual U+FFFD and supplementary characters must remain accepted. The new validator cannot recover Linux filename bytes after lossy managed enumeration; raw directory/readlink/syscall handling remains necessary, including NUL checks and original realpath failure behavior.

System.Text.Json's new facilities do not supply the selected Go JSONv2 responsibilities in [JsonWire](../src/TypeScript.Scanner/Json/Internal/JsonWire.cs), [JsonDiagnosticReader](../src/TypeScript.Scanner/Json/Internal/JsonDiagnosticReader.cs) and [PackageJson](../src/TypeScript.Scanner/PackageJson/PackageJson.cs): raw ReadValue versus WriteValue grammar, duplicate typed-field mutation, skipped unknown-number conversion, nil/empty distinctions, exact errors/pointers/offsets, partial output, depth or Go JSON tag rules. Union support does not infer these contracts. F# union serialization is explicitly reflection-only in the overview and is unsuitable for the accepted NativeAOT path.

Likewise, numeric-converter additions do not remove [JsNum's](../src/TypeScript.Scanner/JsNum/String.cs) ECMAScript binary64 formatting thresholds, negative-zero handling, parsing/rounding or BigInt boundaries, nor semver overflow errors. Any runtime formatter improvement still requires the existing exact numeric expectations; there is no demonstrated benefit here.

## Recommended bounded future experiment

1. In a separately authorized upgrade experiment, first compare the new UTF validators with the **existing strict boundary policy**, using scalar BMP/supplementary/U+FFFD positives and lone-surrogate, truncated, overlong, invalid-byte and NUL cases. NUL is valid Unicode and still needs its separate OS-path rejection. Keep existing exception/error behavior and raw bytes. A validator fast path is useful only if it reduces complexity or cost without an extra transcode/allocation; both performance and allocation benefits are hypotheses.
2. Then assess one authored JSON transport path using static metadata, writer reuse or JSONL. Retain exact ordering, framing, NativeAOT and process-isolation requirements. Do not route compiler/package raw JSON through it.
3. Defer broad Rune/casing/scanner substitutions and numeric changes unless a concrete measured hotspot and an exact semantic equivalence argument emerge.

The first experiment may simplify boundary validation; it will not eliminate the Go-byte compatibility layer or justify adopting .NET 11 by itself. A future SDK/runtime upgrade requires its own complete guarded regression/native run. The existing .NET 10 acceptance is unchanged.
